## 📦 TypeScript Data Contract (Schema 1.1)

> ⏳ **Pending confirmation from TypeScript developer.**
> The interface below is based on the documented `SimulationParameter` structure from the PR review.
> It has not been validated against the actual TypeScript source.
> Please review field names, enum values, and the `source` object structure and report any mismatches.

The `mission_config.json` produced by this pipeline is intended to conform to the following interface:

```typescript
// TypeScript SimulationParameter interface
export interface SimulationParameter {
  parameter_id: string;
  resource?: string;
  system?: string;
  equipment_id?: string;

  // Supported flow types — exactly 8 valid values
  flow_type:
    | "consumption"   // resource consumed by crew/systems
    | "production"    // resource produced (e.g. CO₂ exhaled)
    | "generation"    // energy/resource generated by a system
    | "removal"       // resource removed from environment (e.g. CO₂ scrubbing)
    | "recovery"      // resource recovered/recycled
    | "loss"          // cumulative loss
    | "capacity"      // maximum storable/available quantity
    | "requirement";  // planned requirement / design target

  value: number;      // Finite, non-negative number. TBD parameters are excluded from config (never null or zero substitution).

  // Supported basis — exactly 5 valid values
  basis:
    | "per_person"    // value is per crew member
    | "per_equipment" // value is per piece of equipment
    | "per_cycle"     // value is per operational cycle
    | "per_time"      // value is per time interval (requires period)
    | "total";        // aggregate total

  // Unit must strictly belong to the 17-unit registry
  unit: string;

  // Optional period; mandatory with unit in ('hour' | 'day' | 'cycle') when basis is 'per_time'
  period?: {
    value: number;
    unit: "hour" | "day" | "cycle" | "minute" | "second";
  };

  // Classification and review state are SEPARATE concepts
  classification:
    | "research_data"         // from NASA research / measured data
    | "engineering_inference" // derived from research with engineering assumptions
    | "gameplay_assumption";  // design decision by the development team

  data_status:
    | "mock"            // placeholder / test value
    | "pending_review"  // research value not yet reviewed for simulation use
    | "validated"       // explicitly reviewed and accepted for simulation use
    | "TBD";            // unresolved research status

  source: {
    title: string;
    url: string | null;
    identifier: string | null;    // DOI, NASA document number, etc.
    location: string | null;      // table, section, instrument
  } | null;

  assumptions: string[];  // must not be silently dropped
  caveats: string[];      // scientific qualifications — must not be silently dropped
}

export interface MissionConfig {
  schema_version: "1.1";
  mission: { crew_size: number };
  parameters: SimulationParameter[];
}
```

## ⚠️ Unit Registry for TypeScript Developers

The pipeline strictly emits units belonging to the TypeScript **17-unit registry**:

`["kg", "g", "L", "mL", "kcal", "Wh", "kWh", "W", "kW", "kg/day", "kg/cycle", "L/day", "Wh/cycle", "kWh/cycle", "kg/m3", "ppm", "percent"]`

### Resource-Specific Permitted Units:
- **Oxygen**: `kg`, `kg/day`, `kg/cycle`, `g`
- **CO₂**: `kg`, `kg/day`, `kg/cycle`, `g`
- **Water**: `kg`, `kg/day`, `kg/cycle`, `L`, `L/day`, `g`, `mL`, `percent`, `ppm`
- **Food**: `kcal`, `kg`, `kg/day`
- **Power / Energy**: `Wh`, `Wh/cycle`, `kWh`, `kWh/cycle`, `W`, `kW`

### Excluded Unresolved & Non-Registry Parameters:
Parameters whose units cannot be converted into the 17-unit registry without arbitrary assumptions (e.g. `mSv/day`, `μGy/hour`, `μSv/hour`, `pfu`, `days`, `Earth days`, `years`, `m²`, `astronauts`, `kg/person/year`) or whose values are scientifically unresolved (TBD) are **omitted from `mission_config.json`**. They are tracked in dedicated research reports (`get_unresolved_parameters_report()` and `get_unsupported_unit_parameters_report()`) and in test fixtures rather than polluting the TypeScript simulation engine configuration with invalid units or fabricated numbers.

## ⚙️ Simulation Engine Guidance & Special Semantics

### 1. Canonical Aliases & Preventing Duplicate Calculations
`mission_config.json` includes **5 canonical aliases** designed for the simulation engine's direct key lookups:
- `crew_oxygen_consumption` (0.89 kg/day, per_person) — alias for `daily_o2_requirement_per_astronaut`
- `crew_co2_production` (1.08 kg/day, per_person) — alias for `daily_co2_production_per_astronaut`
- `crew_water_requirement` (5.03 kg/day, per_person) — alias for `daily_water_requirement_per_astronaut`
- `crew_food_energy` (3,000 kcal/day, per_person) — alias for `energy_requirement_per_astronaut`
- `crew_food_mass` (2.39 kg/day, per_person) — alias for `packaged_food_per_astronaut`

> ⚠️ **CRITICAL FOR TYPESCRIPT DEVELOPERS:**
> Access parameters by **exact `parameter_id`** (e.g., `parameters.find(p => p.parameter_id === 'crew_oxygen_consumption')`).
> **DO NOT** compute total consumption by blindly summing all parameters where `flow_type === 'consumption'`, as both the descriptive research parameter and the canonical alias exist in `mission_config.json`. Each canonical alias carries an explicit caveat: `Canonical alias for ...`.

### 2. Water Recovery (98%): Efficiency vs. Quantity
Parameters with `flow_type: "recovery"` and `unit: "percent"` (such as `overall_iss_water_recovery_milestone` = 98.0%, `humidity_condensate_recovery` = 99.0%, `urine_water_recovery` = 98.0%):
- **Must be interpreted strictly as recovery efficiency multipliers** (e.g. $0.98 \times \text{recycled stream mass}$).
- **Must NOT be interpreted as absolute resource quantities** (e.g. do not add 98 kg or 98 L to habitat water stores).

### 3. Accessing Omitted Parameters (22 Unresolved & 21 Unsupported Units)
All 43 omitted research parameters remain completely traceable and accessible:
- **Python Pipeline Reports**:
  - `get_unresolved_parameters_report()` → 22 unresolved parameters (TBD, qualitative, formulas).
  - `get_unsupported_unit_parameters_report()` → 21 parameters with units outside the registry (`mSv/day`, `pfu`, `days`, `m²`).
- **REST API Endpoints**:
  - `GET /api/reports/unresolved`
  - `GET /api/reports/unsupported-units`
- **Reference Fixtures & Sheets**:
  - `tests/fixtures/expected_radiation_calculations.json` (LND dosimetry in silicon & water).
  - `tests/fixtures/expected_life_support_calculations.json` (stoichiometric mass balances).
  - `research-deliverables/simulation-parameter-sheet.md` (complete 66-parameter matrix).

### 4. 16 Emergency Scenarios & Filtering Provenance
From 130 raw NASA DONKI notifications, the pipeline filters specifically for Solar Energetic Particle events (`message_type == 'SEP'`), generating exactly **16 emergency scenarios** in `outputs/emergency_scenarios.json`:
- **Traceability**: Every scenario preserves its NASA DONKI activity ID (e.g. `2024-05-09T13:59:00-SEP-001.`) and unique message ID (`scenario_id: scenario_spe_<message_id>`).
- **NOAA Radiation Storm Scale**: Evaluated from associated solar flare class (S1 through S4).
- **Shelter Protocols**: Each scenario specifies lead times, peak flux in pfu, storm duration, and shelter protection factor requirements.

### Radiation — Important Distinctions

The Chang'e-4 LND instrument measured **two distinct quantities**:
- **13.2 ± 1 μGy/hour** — total absorbed dose rate in silicon
- **57.1 ± 10.6 μSv/hour** — charged-particle GCR dose-equivalent in water

The pipeline computes `57.1 × 24 / 1000 = 1.37 mSv/day` as an **environmental reference rate**.

> ⚠️ This is **not** a human effective dose and **not** a gameplay health threshold.
> Human biological dose requires radiation quality-factor weighting.
> Shelter protection factors and health damage thresholds remain **TBD** (gameplay assumptions).
